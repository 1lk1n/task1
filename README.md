# Микросервис каталога: Next.js + FastAPI + aiogram + PostgreSQL + MinIO

Администратор размещает товар в Telegram-боте одним сообщением (фото + название в подписи), покупатель открывает каталог в браузере или прямо в Telegram как Mini App. Каждый компонент stateless и запускается в нескольких репликах: в `docker-compose.yml` API, бот и фронтенд по умолчанию подняты в двух экземплярах за nginx.

## Состав

| Сервис | Что делает | Реплик |
| --- | --- | --- |
| `bot` | aiogram 3, вебхук. `/start` и любое сообщение: «У меня есть товар» и кнопка Mini App. Администратор: кнопка «Создать товар», затем фото с названием в подписи | 2 |
| `api` | FastAPI: список и карточка товара, создание товара (только для бота, по сервисному токену) | 2 |
| `web` | Next.js App Router: страница «Каталог» и карточка товара, работает в браузере и в Telegram Mini App | 2 |
| `postgres` | товары | 1 |
| `minio` | изображения товаров (бакет `products`, чтение публичное) | 1 |
| `nginx` | единая точка входа и балансировщик: `/` → web, `/api/` → api, `/bot/` → bot, `/media/` → картинки из MinIO | 1 |
| `migrate`, `minio-init` | одноразовые задачи: миграции Alembic и создание бакета до старта реплик | — |

Поток создания товара: Telegram → вебхук → любая реплика бота → скачивает фото в память → `POST /api/products` → любая реплика API → картинка в MinIO, запись в PostgreSQL. Каталог: браузер или Mini App → nginx → любая реплика Next.js → серверный рендеринг с запросом в API → картинки по `/media/...` из MinIO через nginx.

## Почему это работает в нескольких репликах

- **Бот работает через вебхук, а не long polling.** `getUpdates` может вызывать только один процесс (второй получает 409 Conflict), а вебхук Telegram доставляет каждый update в одну из реплик за балансировщиком. Каждая реплика при старте ставит один и тот же вебхук и кнопку меню, повторный вызов ничего не меняет. Telegram ограничивает эти вызовы на бота, а не на реплику: если реплики стартуют одновременно и получают flood control, каждая ждет указанное время и повторяет, а не падает.
- **Нет состояния диалога.** Товар приходит одним сообщением (фото + подпись), поэтому FSM и хранилище состояний не нужны: любую реплику можно убить в любой момент.
- **Повторная доставка не создает дублей.** Вебхук обрабатывается до ответа 200 (`handle_in_background=False`): если реплика упала посреди обработки, Telegram пришлет update снова. Ключ идемпотентности `tg:<chat_id>:<message_id>` уходит в API, а в базе на него стоит уникальный индекс, и вставка идет через `INSERT ... ON CONFLICT DO NOTHING`. Даже если один update одновременно обрабатывают две реплики, товар будет один. Имя файла в MinIO тоже выводится из ключа, поэтому повторная загрузка перезаписывает тот же объект.
- **Никаких файлов на диске.** Бот скачивает фото в `BytesIO`. API принимает изображение телом запроса и читает его в память с ограничением размера: multipart-парсер сбрасывает большие файлы во временный файл на диске, поэтому от него отказался. Изображения живут только в MinIO.
- **Без кэша в процессе.** Страницы Next.js динамические (`force-dynamic`, `fetch` с `no-store`): ни ISR, ни кэша данных на диске, все реплики сразу показывают один и тот же каталог.
- **Соединения, а не данные.** В процессе API живут только пул соединений с базой и клиент S3. Сессия базы своя на каждый запрос (`Depends`), закрывается контекстным менеджером и откатывается при ошибке.
- **Миграции отдельно.** Схему меняет одноразовый контейнер `migrate` до старта API, а не каждая реплика при запуске.
- **Конфигурация только из переменных окружения**, у API и бота есть health-эндпоинты, контейнеры работают от непривилегированного пользователя, образы собираются в несколько стадий.

Масштабирование, например `docker compose up -d --scale api=4 --scale web=3 --scale bot=3`. nginx находит реплики через DNS Docker на каждый запрос, в том числе запущенные позже него.

## Архитектура кода

**backend** (FastAPI), слои зависят только внутрь:

```
app/
  domain.py           сущность Product и доменные ошибки
  ports.py            интерфейсы ProductRepository и ImageStorage
  services.py         сценарии: список, карточка, создание товара (без HTTP, SQL и S3)
  infrastructure/     реализации портов: SQLAlchemy 2.0 async + asyncpg, aioboto3 для MinIO
  api/                роуты, зависимости (сессия на запрос, сервис, сервисный токен), схемы Pydantic v2
  main.py             сборка приложения, lifespan с пулом и клиентом S3
alembic/              миграции
tests/                сценарии на фейковых репозиториях и HTTP-тесты через httpx
```

**bot** (aiogram 3): `handlers.py` (логика и роутер), `catalog_api.py` (клиент API), `keyboards.py`, `main.py` (aiohttp-сервер вебхука). Бот не ходит в базу и хранилище сам, только через API.

**frontend** (Next.js 15, App Router): `app/page.tsx` (каталог, серверный компонент), `app/products/[id]/page.tsx` (карточка), `app/telegram-init.tsx` (клиентский компонент: `Telegram.WebApp.ready()` и `expand()`), `lib/api.ts`. Стилей нет, как разрешено в ТЗ.

## Запуск

Нужен Docker. Telegram принимает вебхуки и открывает Mini App только по публичному HTTPS, поэтому для локального запуска нужен туннель к nginx.

1. Создать бота в [@BotFather](https://t.me/BotFather) и взять токен.
2. `cp .env.example .env` и заполнить: `BOT_TOKEN`, `ADMIN_IDS` (Telegram id администраторов через запятую), секреты.
3. Поднять туннель на порт nginx и вписать выданный адрес в `PUBLIC_URL`:
   ```
   cloudflared tunnel --url http://localhost:8080
   ```
4. Запустить:
   ```
   docker compose up -d --build
   ```
5. Открыть бота в Telegram и отправить `/start`. Администратор видит кнопку «Создать товар»: после нее отправить фото с названием в подписи. Каталог открывается кнопкой «Открыть каталог», кнопкой меню бота или в браузере по `PUBLIC_URL` (локально `http://localhost:8080`).

Без бота, например для проверки API и каталога: `docker compose up -d --build --scale bot=0`.

## API

| Метод | Путь | Описание |
| --- | --- | --- |
| GET | `/api/products` | товары, новые первыми |
| GET | `/api/products/{id}` | карточка товара, 404 если нет |
| POST | `/api/products?title=...` | создание товара. Тело запроса — изображение (`Content-Type: image/jpeg`, `image/png` или `image/webp`, до 10 МБ). Заголовки `Authorization: Bearer <SERVICE_TOKEN>` и `Idempotency-Key` |
| GET | `/api/health` | проверка API и базы |

Документация OpenAPI (Swagger): `/api/docs`.

## Тесты

```
cd backend && pip install -r requirements-dev.txt && pytest
cd bot && pip install -r requirements-dev.txt && pytest
```

В backend сценарии создания (идемпотентность, валидация, порядок каталога) и HTTP-уровень (сервисный токен, лимит размера, повторный запрос). В боте апдейты проходят через настоящий диспетчер aiogram с подмененной сессией Telegram: маршрутизация, фильтр администратора, создание товара одним сообщением.
